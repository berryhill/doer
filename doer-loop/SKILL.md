# Doer Loop

## When to use

Use for a request to run or test this repository's `./doer` executable. Work from the repository root, and read `README.md` and the relevant controller code for the current behavior. This skill describes the checkout's executable; it does not require an installed skill, a gateway command, or a dedicated Doer profile.

## Run one task

1. Choose an existing, fresh, disposable workspace separate from the repository root, with the verification target absent before invocation. State one concrete task and a relative artifact path to check; if exact text is required, specify it too. A pre-existing file may pass the presence/text check without new work. For an existing target such as `SKILL.md`, stage a source copy under a different name and leave the verified path absent; use another fresh workspace for any retry, never the one containing the previous artifact.
2. From the repository root, invoke `./doer 'Create result.txt containing exactly hello in the workspace. No other files.' --workspace "$WORKSPACE" --verify-file result.txt --expect-text hello --execute`, with `WORKSPACE` set to that existing disposable directory. The executable uses this checkout's `.venv/bin/python`; use it only when the project environment and Hermes CLI/model access are already available. Without `--execute`, the command is only a dry run and makes no task changes. A live run requires `--verify-file` and an existing workspace.

   For a live run, give the outer caller enough time for the whole controller lifecycle, not merely one Hermes chat's 300s run budget or 360s subprocess timeout: up to three sequential implementation attempts, Laya decisions, possible Luna diagnoses, and Luna completion can accumulate. Run as a tracked process, retaining stdout, stderr, and exit code; wait for it to exit before parsing its final stdout JSON. Only then report the JSON `status`, `attempts`, trace, time, and cost, cross-checking the exit code; stderr contains a human-readable report (a dry run prints no JSON). An inner Hermes timeout normally becomes a controller `error` with a Luna completion attempt; an outer caller timeout is not Doer's outcome. On caller timeout, inspect whether Doer is still running or was stopped and preserve its output. If process state cannot be established, or it exits without final valid JSON, the outcome remains unknown; do not infer success, `incomplete`, or failure from a partial log or an existing artifact. Do not start a second invocation while the first may still be running, and never retry in its old workspace.
3. Laya is the default typed decision backend for the task gate and judgment, loaded in-process; no Laya server is needed. The stable implementation default is Sol. Experimental family routing is opt-in via `--routing-policy laya` with repeated `--available-model NAME` values confirmed on the active account/provider; `--routing-policy rules` is a deterministic comparator. Only GPT-6 Astra, Sol, Luna and their Hermes `-900k` aliases are candidates. Doer does not fetch entitlements at runtime: availability is operator-asserted; the default Sol assumption is marked unverified. Laya chooses only an eligible family, once after the gate. Byte length of the first implementation prompt is observable, but bytes are not tokens and later tool reads/retry context are unknown. An alias requires a separately operator-reported measured token count via `--observed-input-tokens` and confirmed alias availability; this is not proof of a context requirement. Invalid/uncertain family answers fall back to confirmed Sol or stop safely. Diagnosis and final assessment remain `gpt-6-luna`; at most three implementation attempts occur. A failed gate yields `needs_input` without selection, and exhausting attempts yields `incomplete`.
4. Hermes roles inherit the ambient profile, provider, and credentials. Supply only intended overrides: `--profile NAME`, `--provider NAME`, `--sol MODEL` (bypasses routing), and `--luna MODEL`. Overrides do not create model access or credentials. Hermes `-900k` variants are client-side aliases, not provider-returned IDs. `--backend jev` is optional only when its API credentials are already securely configured outside the repository; do not put credentials in prompts or files.

## Interpret and verify

- Read the CLI JSON `status`, `attempts`, `completion`, and `trace`, and check the exit status: only `verified` exits successfully. `completion` is Luna's one-sentence assessment when available; `completion_error` records a failed completion report without changing the outcome. `error` indicates a model/controller failure. The ordered trace includes gate, model selection (availability source, constraints, measured bytes, context uncertainty, family proposal/fallback, selected name), implementation (Hermes-reported actual model), judgment, independent verifier, Luna diagnosis when needed, and Luna completion, with timing, evidence/errors, model/provider, session, tokens, and cost. Do not treat an uncalibrated Laya score as a success probability. Cross-check Luna's claims against the trace: a completion sentence can mention a backend that was not run.
- Doer's independent verifier checks only one user-selected regular file inside the workspace. It rejects absolute paths, parent escapes, and symlink paths. Without `--expect-text` it checks presence; with it, it compares UTF-8 text after stripping outer whitespace. It does not validate other artifacts, behavior, test results, side effects, or code quality. Laya judges the implementer's report, not the actual implementation. No prompt or verdict is a sandbox: Hermes may inherit ambient tools and permissions. Review the workspace and run task-specific checks independently before reporting success.
- For an artifact, independently inspect the chosen file and execute relevant checks. For the offline suite, run `.venv/bin/python -m unittest discover -v`. `eval_model_selection.py --results-dir "$DIR"` shows a snapshot-based development/held-out comparison against always-Sol and deterministic rules; its unmeasured diagnostic hypotheses are not best-model labels. Run each case/policy only with confirmed access, fresh workspaces, retained controller JSON and independent acceptance; summarize whole-loop outcomes, attempts, time, tokens and cost, including failures and ties. The initial three measured paired cases showed no Laya advantage, so keep routing opt-in. The optional real-model smoke invokes live models and requires access. `--test-retry-once` injects a synthetic failure; never use it for real tasks.
- Compare the source checkout's `git status --short` before and after a live run and inspect the workspace for unrelated changes. At completion Doer prints a human-readable report to stderr and also includes it as JSON `report` on stdout; stdout stays machine-readable. In your final response, include its outcome, every step's model/provider, time, tokens, verdict/error, and cost status, plus total time/cost, even if the user did not ask again for stats. Do not just cite the JSON path or say "verified"; cross-check report claims against `trace`, explain absent steps (such as no diagnosis on first-attempt success), and independently show a small safe artifact's actual content, not only its path. The report repeats trace evidence, may contain sensitive text, and is not an independent check: excerpt or redact sensitive/large material. Distinguish subscription-included charges, unknown prices, and unpriced local compute. Report failures and blockers plainly. Do not ask Doer to install dependencies, commit, push, deploy, or write to external systems; perform any separately authorized publication yourself after independent review. A workspace instruction is not security isolation.
